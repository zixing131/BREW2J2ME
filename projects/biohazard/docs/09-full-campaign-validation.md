# 0.3.10 全主线连续通关验证

日期：2026-10-30。运行代码保持 0.3.10，本次增加可重复的连续通关测试，没有降低敌人伤害或修改任务条件。

## 结论和条件

**商城补给辅助下，生产游戏逻辑和三个分辨率的生产 Canvas 均能从新游戏连续走到原版结局。** 这次不再只是分别加载 16 张地图。

验证角色使用剧情获得的普通武器；通过游戏现有的离线商城购买两次生命提升（50→100→200）、12 次金钱兑换、一次原完整版解锁，另在随身商店购买 690 份药品、68 份 50 发弹药。未购买超级武器、无限弹药或隐身。大量购买是自动玩家战斗策略的限制，不能据此认定普通经济和难度已经验证。

不使用商城补给的自动玩家在医院第 852 帧、主线进度 4 时死亡。它不是熟练玩家，死亡不能证明普通流程无法通关；但本次也**没有证明不依靠商城能通关**。

这是桌面 Java 测试适配器驱动生产代码的结果，**不是 KEmulator 或真机人工全关通关**，也不是原版同输入录像差分。完整触屏操作、真机内存/帧率、实际连续音频播放仍未由本测试覆盖。

## 连续路线和原版结束条件

路线根据 `docs/reverse/scripts.json` 中的 11000—11015 原脚本确定；游戏实际读取 `resources/original` 数据。

| 阶段 | 实际经过的地图 | 必须完成的任务 |
|---|---|---|
| 医院 | 1→2→3 | 开场教学、消防斧、指定丧尸死亡、钥匙、左轮、医院出口 |
| 寻找幸存者 | 3→4→5→4→3→4→5→6→7→8→9 | 警局武器、公园通讯、返回救人、两名幸存者、基地外指定敌人死亡、抵抗组织 |
| 通讯设备 | 9→8→7→10→11→12→13→12→11→10→7→8→9 | 取得 AWP、登财金大厦取通讯设备、回基地接电池任务 |
| 电池 | 9→15→16→15→9 | 电器店五个电池点、取得可用电池、回基地联络总部并取得 M4 |
| 撤离 | 9→8→7→6→5→4→3→4→5→6→7→10→11→12→13→14 | 医院撤离失败、改道财金大厦、到达天台并触发结局 |

地图编号不等于线性的关卡顺序。真正的结局在地图 **14**：资源 11013 的事件 0，位置 `(28,1)`，主线变量 `variables[0] == 35`，原脚本操作码 50 置 `vm.ended`。地图 15、16 属于中途电池任务。

两类测试均要求：角色仍存活、16 张地图访问掩码为 `0xffff`、地图为 14、主线变量为 35、`vm.ended == true`。只进入最后地图不算成功。

## 测试方式

### 生产逻辑连续运行

`j2me/tests/FullCampaignTest.java` 从 `new OriginalSession` 开始，沿脚本目标寻路，发送正常移动/转向/射击，确认对话和转场，调用生产药品与购买接口。它不传送、不写玩家生命或任务变量、不直接杀死敌人、不替换任务执行位置。

寻路预测只修改复制的碰撞网格。输入驱动层对剧情购买确认清除 `action.kind/offer`，对打开商店清除开火锁存，明确模拟 `OriginalCanvas` 对应操作；这部分单独不能证明 UI 可用，因此还需要下面的完整界面回放。

在每次地图或主线进度变化，以及最终结束时生成完整快照。连续运行和每个检查点实际 `SaveCodec.decode` 恢复后继续运行各做一轮，检查快照字节往返无损，并要求两轮操作轨迹及全部检查点状态 CRC 完全一致。CRC 计算不包含快照末尾已有的 CRC 字段。

本次两轮均为 **55,228 个更新帧、81 个检查点、3,535 次实际攻击、938 次敌人死亡、690 次用药**；恢复轮实际替换会话 81 次。检查点数量为这条固定路线的实测值，不代表 81 个独立关卡。

### 生产 Canvas 全操作回放

`j2me/tests/CampaignCanvasTest.java` 读取上一步生成的操作轨迹。从封面和“开始游戏”进入，使用生产 `keyPressed/keyReleased` 驱动移动、射击、对白翻页、购买确认、随身商店和药品。反射仅用于读取私有状态、停下后台计时器和调用生产 `tick()`，不设置界面选择、玩家或剧情状态。

每个检查点校验完整序列化状态 CRC 与逻辑运行一致，调用生产 `OriginalSaves` 做 RMS 写入/读出并比较全部快照字节；每 1,000 帧和每个检查点执行实际绘图。最后检查实际界面的“恭喜完成全部任务”、结局自动存档，并从主菜单“继续游戏”载入该自动记录。

| 分辨率 | 更新帧（含结局重载后 1 帧） | 匹配检查点 | 按键点击 | 结果 |
|---|---:|---:|---:|---|
| 240×320 | 55,229 | 81 | 26,716 | 全流程、结局和 RMS 通过；默认无虚拟键盘 |
| 320×240 | 55,229 | 81 | 26,645 | 全流程、结局和 RMS 通过；默认无虚拟键盘 |
| 360×640 | 55,229 | 81 | 26,834 | 全流程、结局和 RMS 通过；默认开启触控布局，本轮输入仍为键盘 |

点击数量不同来自各尺寸的对话分页；游戏状态在检查点仍相同。最后角色生命 160/200、金钱 4,086。已经人工查看三个尺寸的结局图和战斗取样图，文字及操作区可见。

## 重现

从仓库根目录：

```sh
python3 tools/project.py test biohazard
```

该命令重新构建并执行 CLDC 预校验，再运行原有 ARM 差分、核心、Canvas/RMS、音频测试，以及新增的两轮主线和三轮界面回放。失败会使命令返回非零。

产物保持 `j2me/dist/BiohazardDemo.jar` / `.jad`，版本 0.3.10。测试类和桌面 API 适配器不打包进 JAR。

可重复生成的证据保存在被 Git 忽略的 `j2me/build/`：

- `full-campaign-shop.log` / `full-campaign-shop-resume.log`：每次转场、主线变化和购买日志。
- 对应 `.inputs`：每帧输入、菜单动作和检查点状态 CRC。
- `campaign-ui/{240x320,320x240,360x640}/`：阶段取样、`ending.png` 和 `ending-reloaded.png`。这些是生产 Canvas 的桌面渲染图，不是模拟器截图。

单独尝试无商城辅助（在 `j2me/` 目录，先执行过完整测试，`J2ME_JDK_HOME` 使用本地工具链配置）：

```sh
"$J2ME_JDK_HOME/bin/java" -Xmx512m -cp build/tests \
  bio.original.FullCampaignTest resources/original build/full-campaign-normal.log
```

不带 `shop` 参数即不会主动购买生命提升和兑换金钱；如果到达原完整版提示，仍可确认该剧情解锁。当前自动玩家会在医院失败，此模式未作为通过的回归基线。
